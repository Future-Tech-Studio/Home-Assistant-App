# Future Homes Tech app: loading and reliability review

Reviewed September 10, 2026 (America/Phoenix). Installed version observed: **0.4.98**. Fix candidate: **0.4.99**. User-designated stable rollback: **0.4.80**, unchanged.

## What actually slows the opening

The live Home Assistant sidebar first opens an ingress iframe. Version 0.4.98 initializes the full application there, then `enterKioskMode()` navigates the entire browser to the same app and initializes it again. Two startup log entries appeared 307 ms apart during the live check. This confirms duplicate initialization, not that the entire reported four-to-five-second wait is caused by that one operation.

The old document contains **373,839 bytes** of markup, CSS, and JavaScript, compressed to **65,618 bytes**. CSS and JavaScript cannot be cached independently of that document. Every app opening must fetch the document again, with a new CSP nonce.

Other confirmed contributors:

- `requestIdleCallback(..., {timeout})` specifies the latest allowed execution time, not a minimum delay. The prior warmups could all begin immediately; the Safari fallback explicitly reduced every delay to at most 500 ms.
- The browser fetched the complete entity inventory to calculate one remaining menu count: offline climate devices. The backend already maintains a shared inventory.
- Lighting reads copied the whole inventory again and reread Home Assistant registry files on each projection, despite already-enriched cached metadata.
- A disconnected, expired backend cache blocked ordinary reads behind a full upstream refresh, which can wait up to 30 seconds.
- Every live long-poll could occupy one of the same 16 HTTP workers used for page delivery. Overload handling additionally blocked the accept loop for up to a second per request.
- The old “shell interactive in 0ms” timer started at the end of initialization. It did not measure navigation-to-shell time.

Home Assistant's own ingress/session preparation is a separate part of the opening path. It still needs a post-install measurement on the actual wall controller; local preview timings cannot certify that part.

## Changes in 0.4.99

| Change | Effect |
| --- | --- |
| Minimal iframe kiosk handoff | The intermediate document is approximately **778 bytes**, without application code or API calls. If iframe fetch metadata is absent, the early redirect and module guard still avoid initializing the app twice. A blocked top-level redirect has an embedded fallback. |
| Fingerprinted CSS/JS with compression and immutable caching | The shell becomes approximately **16.4 KB**, or **3.4 KB compressed**: about **95% less repeat-navigation HTML transfer**. This is not a 95% reduction in all cold-start assets or a promised 95% speedup. New asset hashes invalidate caches on update. |
| Real staggered warmups and in-flight GET coalescing | Background requests do not all start at once; identical simultaneous reads share one request. Mutations are never coalesced. |
| Compact offline-menu endpoint | No full browser entity download merely to count offline thermostats. Full inventory remains available to editors that need it. |
| Background stale-cache recovery | Existing snapshots return promptly and remain explicitly marked stale until recovery. Security indicators continue to reject stale data. Explicit forced refresh still waits for a real refresh. |
| Cached lighting projection | Removes redundant full-copy/registry-read work while preserving metadata refresh through the existing registry event subscription. |
| Live subscription and revision fixes | State events interleaved with subscription acknowledgements no longer incorrectly reject the connection. A restarted server with a lower revision immediately tells existing clients to resynchronize. |
| Reserved request capacity | Limits waiting live polls separately from page/API workers; overload returns immediately with a correct response length. |
| Refresh/error fixes | Forced Home Configurator refresh reaches its loader; changing pages mid-refresh no longer changes its target; rejected background refreshes are handled; missing temperature is not converted to 0 degrees. |
| Device Alarm save locking | The enhanced output picker is disabled with its underlying selector during a save, preventing silently discarded checkbox edits. Automation behavior is unchanged. |
| Honest instrumentation | Console diagnostics show navigation-to-shell time, module time, document TTFB, and slow/failed API requests without logging query values or payloads. Browser cancellations do not generate server tracebacks. |

## Verification and boundaries

- The complete release gate checks Python compilation, source and served JavaScript syntax, bootstrap syntax, regression tests, release versions, and expected runtime assets.
- New behavioral tests cover kiosk fallback, cache headers/304 responses, changed asset hashes, missing assets, restart revisions, stale recovery, interleaved live events, long-poll capacity, overload framing, compact menu counts, cancelled requests, GET coalescing, actual idle scheduling, forced refresh, temperature fallback, and alarm-picker save locking.
- A localhost-only preview with fake devices rendered the unchanged dashboard shell correctly. Recorded shell-ready times were **68–153 ms**; the 0.4.99 preview recorded **152 ms** on its first new-hash load. These are local development measurements, not installed Home Assistant benchmarks.
- The live 0.4.98 Home Configurator showed Whole Home, First Floor, and Second Floor from its preloaded index. Protect showed **Unavailable**, security mode **Unknown**, and Exterior was unavailable. The Protect page reported “Unable to read Protect arm-mode status.” This review did not establish whether that live failure is a credential, certificate, network, or upstream API issue. No security setting was weakened to hide it.
- The separate Home Assistant Wall Controllers dashboard visibly has many `Entity not found` cards, including old lighting/climate/media references. Those external dashboard definitions were not edited.
- No physical lights, chimes, sirens, armed modes, Matter/Thread settings, or automations were activated as tests. Runtime installation and homeowner acceptance are separate from mounting the release source.

## Next 15 suggested changes, in priority order

1. **Resolve the live Protect and Exterior status failures.** Add operator-facing error details and last-good timestamps, then test the actual configured endpoint/certificate and expected door set. Keep unavailable states truthful; do not turn off TLS checks as a shortcut. Evidence: live Unifi page and toolbar.

2. **Audit and safely repair obsolete entity/group references.** Produce a dry-run report of missing targets, duplicate generated versus legacy helpers, and saved actions referring to removed devices. Offer reviewed migrations, not automatic deletion. Evidence: live Wall Controllers errors and overlapping old/new helper names. Preserve the stable backup.

3. **Return the shared action catalog once per revision.** Every room response currently reconstructs and includes whole-house action choices. Give that catalog a versioned endpoint and reuse it across rooms; return only room-specific settings with each room. Evidence: `FutureHomesTechRequestHandler._home_configurator_room()` and `_shared_action_catalog()`.

4. **Load each room subsection only when expanded.** Opening a room builds Buttons, Switches, Presence, Door Actions, Room Modes, and Wake-up content even when their cards remain closed. Render section headers first, then populate the selected subsection while preserving drafts. Evidence: `buildRoomConfiguratorBody()`.

5. **Warm button discovery independently.** Room loading waits on `ButtonDeviceInventory.fetch()`; an expired cache performs discovery while holding its lock. Prewarm it in the backend and allow room display to continue if a discovery refresh is slow or unavailable. Evidence: `ButtonDeviceInventory.fetch()` and `_home_configurator_room()`.

6. **Coalesce Home Assistant registry-change bursts.** Each entity/device/area/floor registry event currently triggers a full inventory refresh in the live reader. Batch closely spaced events into one metadata refresh so a device rename or adoption does not create a refresh storm. Evidence: `EntityInventory._run_live_updates()`.

7. **Use an ID-indexed state cache.** Each state event currently rebuilds a dictionary from all entities and sorts the entire result. Maintain the dictionary as the primary representation and sort only the requested projection. Evidence: `EntityInventory._apply_state_changed()`.

8. **Invalidate settings caches by revision and pause hidden-page work.** Long-lived `loadedViews` and cached catalogs can outlive changes made in another browser; hidden tabs also keep live subscriptions and several timers. Revalidate affected data on focus or revision change without collapsing editors. Evidence: `loadedViews`, `settingsApiPayloads`, and `watchLiveStateRevisions()`.

9. **Optionally restore a last-good navigation snapshot.** A browser refresh discards the in-memory floor/room maps. Persist only safe, versioned navigation metadata with a visible stale state, then reconcile in the background. Do not persist credentials or present cached door/alarm state as current.

10. **Remove retired editor code after a migration check.** Hidden standalone room-mode renderers, old detail-card styling, save-all handlers, and historical load-configuration paths remain. Remove unreachable UI first; retain any backend compatibility path still referenced by saved settings. Evidence: `renderBedroomModeCard()`, `loadRoomModes()`, and `saveAllRoomModes()`.

11. **Split the monolithic application by feature.** Fingerprinted assets improve delivery now, but the maintained source still combines a large UI and server into single files. Separate transport/cache, catalogs, configuration storage, and room editors so changes can be reviewed and tested in isolation.

12. **Reduce expensive visual effects on slower wall panels.** Many nested cards use backdrop blur. Offer a reduced-effects style using the same colors and layout, and measure scroll/frame performance on the actual panels before choosing defaults. Evidence: repeated `backdrop-filter` rules in `web/index.html`.

13. **Separate installer privileges from homeowner controls.** The backend currently verifies ingress-proxy origin, not per-operation user roles. Review which authenticated ingress users can regenerate configuration or change installer settings; enforce permissions through trusted Home Assistant identity rather than user-supplied headers. Existing nonce CSP, bounded bodies, and default TLS verification should remain.

14. **Verify every selectable mode end-to-end.** The regular Room Modes save route writes the enabled-mode list and returns `activated: true` without invoking the bedroom automation generator in that branch. Make the distinction between “available to select,” “helper created,” and “mode active” explicit; add integration tests for Sleep, toddler, wake, and armed-mode assignments before changing their behavior.

15. **Add alarm failsafes and Home Assistant runtime acceptance tests.** Temperature clear triggers are strictly below the threshold, and a sensor becoming unavailable is not a clear trigger. Define what happens at equality, sensor failure, restart, and disable; offer an explicit maximum siren duration and test generated YAML plus the full save/activate/clear lifecycle using simulated devices.

## Installation acceptance

Install 0.4.99 from the mounted add-on source, then use the existing refresh-needed control. Open Future Homes Tech from Home Assistant, open Home Configurator, expand a floor and room, and leave an editor open through a live update. Confirm that it does not collapse. Check `[FHT startup]` and `[FHT request]` logs on the actual client for remaining ingress/API delays. Keep 0.4.80 designated stable until the homeowner explicitly approves a replacement.
